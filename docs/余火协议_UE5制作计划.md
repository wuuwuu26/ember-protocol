## 0. 一页速览

### 0.1 项目基线（已确认）

| 项目 | 定义 |
|---|---|
| 品类 | 第三人称动作冒险 ＋ 机体模块化改装 |
| 平台 | PC 单机，键鼠优先，同步支持手柄 |
| 目标玩家 | 动作探索玩家：喜欢改装、探索、剧情，接受中等难度，不追求极限操作 |
| 单局时长 | 20—40 分钟完成一次"准备 → 战斗 → 回收 → 改装"完整弧线 |
| 引擎 | Unreal Engine 5.8 |
| 商业模式 | 买断制，离线单人，无内购 |

### 0.2 Fun Hypothesis（所有设计的地基）

> **这游戏好玩的核心是：每一次拆卸敌人的身体，都在改写你自己的身体，以及你接下来能走的路。**

写不清楚这一句就不往下走。上面这句话的作用是：它把"战斗"和"改装"和"探索"焊成了一个因果链，而不是三个并列系统。

### 0.3 设计支柱（3 条，技术决策的过审标准）

| # | 支柱 | 判定问题（不通过就砍） |
|---|---|---|
| P1 | **改装改变玩法，不只是数值** | 这个新机体／模块带来了新的移动方式或战斗解法吗？只加 5% 攻击力的模块一律砍掉。 |
| P2 | **拆解是有代价的选择** | 这个可回收部件伴随机会成本吗？（救同伴／留资源／换路线）没有取舍的回收只是捡垃圾。 |
| P3 | **20—40 分钟一个完整弧线** | 这个任务包含准备、张力、回收、改装反馈四个节拍吗？缺节拍就重排。 |

### 0.4 时间轴总览

| 阶段 | 周期 | 一句话目标 | 团队规模（规划） |
|---|---|---|---|
| P0 管线与预研 | 第 1—2 月 | 引擎管线跑通，最大技术风险验证完毕 | 6—8 人 |

## 1. 引擎与插件选型

### 1.1 为什么是 UE 5.8

UE 5.8 于 2026 年 6 月发布，是 **UE5 计划内的最后一个版本**，此后 Epic 转向 UE6。对一个 42 个月的项目来说，这是当前最稳的选择：

- **5.8 是长期维护终点**：Epic 会持续为 UE5 提供缺陷修复，不会出现"项目做到一半引擎停止支持"的断层。
- **关键能力已生产就绪**：MegaLights（多动态光源，工业/霓虹场景的核心）、Mutable（运行时角色组装）、Iris 复制、Chaos 布料、Audio Insights。
- **UE6 迁移窗口可预留**：在 P4 阶段安排 2 个月评估期，届时再决定是否迁移。不要现在赌 UE6。

**明确不做的决定**：不在开发中途升级引擎大版本。引擎升级只在 P0 和 P4 两个窗口进行。

### 1.2 核心插件选型表

| 需求 | 选型 | 状态 | 理由 | 风险／代价 |
|---|---|---|---|---|
| 移动基础 | **Character Movement Component (CMC)** | 稳定 | Mover 尚未生产就绪，CMC 官方承诺长期支持 | 攀爬需自定义 MovementMode，工作量前置 |
| 移动（未来） | Mover 插件 | 从实验性向稳定演进 | 架构更干净、预测与重模拟更好 | **当前不用**，P4 再评估；移动逻辑走接口抽象预留迁移 |
| 机体模块装配 | **Mutable** | **生产就绪** | 运行时组装模块化网格、自动 LOD、Epic 官方支持 | 学习曲线；需自写 GameplayTag → 参数的桥接层 |
| 技能与属性 | **Gameplay Ability System (GAS)** | 稳定 | 电力／热量／技能冷却天然适合 AttributeSet + GameplayEffect | 上手陡峭；网络部分用不上（单机）可裁剪 |
| 输入 | **Enhanced Input** | 稳定 | 输入映射与上下文切换，手柄/键鼠统一 | 无 |
| 敌人 AI | **StateTree** ＋ AI Perception ＋ EQS | 稳定 | UE5 推荐的状态驱动 AI，比行为树更适合"有阶段变化"的敌人 | 社区资料少于行为树，需内部沉淀文档 |
| 场景破坏（表演） | **Chaos Destruction** | 稳定 | 用于巨像关卡等特定表演段落 | 性能昂贵，**不做全场景破坏** |
| 环境光照 | **Lumen** ＋ **Lumen Lite** | Lite 为测试版 | Lite 速度快约 2 倍，作为中低画质档；高质量档用完整 Lumen | 需两套画质预设分别验证 |
| 多动态光源 | **MegaLights** | **生产就绪** | 工业场景大量光源（焊火、指示灯、霓虹）的核心 | 需按场景设光源上限 |
| 静态几何 | **Nanite** | 稳定 | 环境巨构的细节密度 | **骨骼网格体不依赖 Nanite**，走标准 LOD 管线 |
| 开放区域 | **World Partition ＋ HLOD** | 稳定 | 大型区域流送；5.8 新增 World Partition Insights 流送调试 | 线性关卡不用它（见 3.7） |
| 环境铺量 | **PCG** | 稳定（部分实验性节点慎用） | 废墟残骸、植被、管道散布 | 实验性节点不进生产管线 |
| UI | **Common UI ＋ MVVM** | 稳定 | 改装界面是核心 UX，需要可维护的数据绑定 | 需早期定 ViewModel 规范 |
| 音频 | **MetaSounds ＋ Quartz** | 稳定 | 机器人语音合成感、引擎声随负载变化 | 无 |
| 动画次级运动 | **Control Rig Physics** | 测试版 | 天线、线缆、液压管的自然摆动 | **测试版，需有回退方案**（退回手 K 动画） |
| 动画重定向 | **IK Retargeter ＋ RigMapper** | RigMapper 为测试版 | 3 类机体共享动画资产 | 主流程用 IK Retargeter，RigMapper 仅试验 |
| 过场 | **Sequencer ＋ Movie Render Queue** | 稳定 | 剧情演出与宣传素材 | 过场数量要严格控制（见 3.11） |
| 模块化游戏功能 | **Game Feature Plugins** | 稳定 | 区域内容可选装，控制打包体积 | 团队小于 30 人时属过度设计，P3 起再评估 |

### 1.3 三个明确的技术取舍

**取舍一：Mover 不用，但留接口。**
Mover 在 5.8 仍被官方描述为"从实验性状态向稳定架构演进"，没有被标注生产就绪。一个 42 个月的项目不该把移动系统押在未定型的插件上。做法是：定义 `IRobotLocomotion` 接口，CMC 作为实现；攀爬、磁吸、冲刺都通过接口调用。将来迁移 Mover 时替换实现层，不动上层玩法代码。

**取舍二：部位拆解用"假拆解"，不用 Chaos 破坏。**
Chaos 逐部件碎裂在几十个敌人同屏时性能不可控，且掉落的碎块无法作为可拾取物稳定回收。做法见 3.2——骨骼隐藏 ＋ 预制备件模型替换。Chaos 只留给巨像关卡的脚本化表演。

**取舍三：机体用独立角色，模块用挂点。**
不要追求"任意零件自由拼接"——那是内容成本的深渊。3 类机体（轻/中/重）各做一个完整 SkeletalMesh ＋ AnimBP；40 个模块通过骨骼 Socket 挂载。只有当模块需要改变骨架比例或合并蒙皮时，才引入 Mutable。

### 2.2 C++ 模块划分原则

| 模块 | 职责 | 依赖方向 |
|---|---|---|
| `RobotCore` | 纯数据类型、GameplayTag 声明、Primary Data Asset 基类 | 不依赖任何其他游戏模块 |
| `RobotAssembly` | 机体装配、模块挂载、Mutable 桥接 | → Core |
| `RobotCombat` | GAS、伤害路由、部位 HP | → Core, Assembly |
| `RobotAI` | StateTree、感知、EQS | → Core, Combat |
| `RobotWorld` | 流送、基地、区域管理 | → Core |
| `RobotUI` | ViewModel、控件基类 | → Core（**不直接依赖 Combat**，通过接口读数据） |
| `RobotSave` | 存档序列化、版本迁移 | → Core |

**硬规则**：依赖只能单向。`RobotUI` 不允许 `#include` `RobotCombat` 的头文件——UI 通过接口或事件拿数据。这条规则能防止后期 UI 与玩法互相纠缠到无法重构。

### 2.3 蓝图 / C++ 边界规则

这是最容易失控的地方，必须在第 1 周就写死规则：

| 内容 | 用 C++ | 用蓝图 |
|---|---|---|
| 核心系统逻辑（装配、伤害、存档、AI 决策） | ✅ | ❌ |
| 数据资产定义与校验 | ✅ | ❌ |
| 数值调参、曲线、掉落表 | ❌ | ✅ |
| 关卡脚本、触发器、一次性演出 | ❌ | ✅ |
| UI 布局与样式 | ❌ | ✅ |
| 原型验证（P0—P1 阶段） | ❌ | ✅ 允许快速试错，进 P2 前重写 |

**禁令**：不允许在蓝图里实现核心玩法逻辑后再"有空再搬到 C++"。原型期的蓝图必须在 P2 之前重写，否则性能与可维护性会在 P3 爆掉。

### 2.4 数据驱动规范

所有可调内容走 **Primary Data Asset**，不散落在蓝图默认值里：

```
URobotChassisData : UPrimaryDataAsset
  ├─ ChassisTag          (GameplayTag: Chassis.Light)
  ├─ Mass                (float, kg)
  ├─ PowerCapacity       (float)
  ├─ HeatCapacity        (float)
  ├─ BaseMovementParams  (FChassisMovementParams)
  ├─ SocketLayout        (TArray<FModuleSlotDef>)
  └─ UnlockCost          (FEconomyCost)
```

好处：策划改数值不需要打开蓝图；可以用编辑器工具批量校验（例如"所有机体必须有 4 个槽位"）；数值可导出成 CSV 做平衡分析。

### 2.5 版本控制与持续集成

| 项目 | 方案 | 理由 |
|---|---|---|
| 版本控制 | **Perforce Helix Core**（首选）或 Epic 内置 **Unreal Revision Control** | UE 资产是二进制，Git 处理大文件会痛苦。团队 > 15 人用 P4，小团队可用 URC |
| 资产锁 | 强制 Checkout／Lock | 防止两人同时改同一个 uasset 导致冲突 |
| 大文件 | 二进制资产走 P4 或 Git-LFS，禁止直接进 Git 主库 | 避免仓库膨胀 |
| 编译加速 | **Unreal Build Accelerator (UBA)** ＋ 分布式编译 | 大型 C++ 工程编译时间直接决定迭代速度 |
| CI | **Unreal Horde ＋ BuildGraph** | 每日自动出包 |
| 自动化测试 | **Gauntlet** ＋ Automation Spec | 冒烟测试：启动、加载、存档读写、关键关卡可通 |
| 数据校验 | 自研 Editor Validator | 每次提交前校验命名、槽位、LOD、材质槽 |

**每日构建的验收线**：能启动 → 能进主基地 → 能进一个区域 → 能战斗 → 能改装 → 能存档读档。任一环断了当天修。

## 3. 核心系统实现方案

### 3.1 机体与模块装配

**目标体验**：玩家在改装界面拖动一个部件，立刻在预览里看到机体形态变化，并能读到重量／供电／散热三条约束的实时反馈。

**实现分层**：

| 层级 | 内容 | 实现 |
|---|---|---|
| 机体（Chassis） | 轻型双足 / 中型通用 / 重型四足，共 3 类 | 独立 `ARobotCharacter` 子类 ＋ 独立 SkeletalMesh ＋ 独立 AnimBP |
| 模块（Module） | 头部、核心、双臂、底盘、辅助，共约 40 个 | 骨骼 Socket 挂载，`UStaticMeshComponent`／`USkeletalMeshComponent` 子组件 |
| 工具（Tool） | 战场快拆工具，少量 | 手部 Socket，运行时切换 |

**关键约束设计（这是支柱 P1 的落点）**：

| 约束 | 作用 | 设计意图 |
|---|---|---|
| 重量 Mass | 影响移动速度、跳跃高度、受击位移 | 让"重装"真的变笨重，而不是纯收益 |
| 供电 Power | 所有主动模块共享上限 | 强制取舍：不能同时装满高耗能模块 |
| 散热 Heat | 决定连续输出时长 | 制造"爆发—停顿"的战斗节奏 |

三条约束互相牵制，是防止"一套最优解通吃"的核心机制。**没有这三条，40 个模块就是 40 个数值贴纸。**

**Mutable 的引入时机**：
- P1 阶段：先用 Socket 挂载方案（简单、可控、够用）。
- P2 阶段评估：如果出现"模块需要改变骨架比例"或"合并蒙皮以减少 draw call"的需求，再引入 Mutable。
- 判断标准：Socket 方案下 draw call 超标，或美术需要做形变类模块。

### 3.2 部位拆解与伤害路由

**目标体验**：玩家瞄准敌人腿部而非躯干，打掉后敌人真的会瘸，而不是扣更多血。

**实现方案**：

```
命中检测
  └─ 命中骨骼名 (FName BoneName)
       └─ UPartMapData (DataAsset): BoneName → FGameplayTag (Part.Leg.R)
            └─ UPartDamageComponent: TMap<FGameplayTag, FPartHealth>
                 └─ 部位 HP 归零
                      └─ 表现层: HideBoneByName() + Spawn 掉落物 Actor
```

**为什么部位 HP 不放进 GAS AttributeSet**：部位数量是动态的（不同敌人部位数不同），AttributeSet 适合固定属性。用独立组件管理，GAS 只负责通过 GameplayEffect 把伤害投递进来。

**"假拆解"的具体做法**：
1. Physics Asset 中每个部位一个 body，命名规范 `part_upperarm_R`。
2. 部位破坏时，`HideBoneByName` 隐藏该部位骨骼。
3. 同时 Spawn 一个预制的**备件模型**（物理模拟），落地后转为可拾取状态。
4. 不使用 Chaos 逐块碎裂——碎块不可控，且无法稳定作为拾取物。

**具名敌人（可修复／可招募）**：额外挂 `UCompanionCandidateComponent`。当部位 HP 归零但核心未毁时，进入"可修复"状态，玩家选择修复（消耗资源、获得同伴）或拆解（获得稀有核心）。这是支柱 P2 的落点。

**边界情况必须处理**：
- 部位全毁但核心存活 → 敌人进入"瘫痪"而非死亡，可交互。
- 玩家自身部位被毁 → 临时失去对应能力（手臂毁则无法使用该臂武器），任务结束自动修复。
- 同一部位多次命中 → 伤害不溢出到其他部位，防止"打腿等于打全身"。

### 3.3 电力与热量（GAS 实现）

**AttributeSet 定义**：

| 属性 | 类型 | 作用 | 初始值 |
|---|---|---|---|
| `Power` | 当前电力 | 技能消耗 | `[PLACEHOLDER]` |
| `PowerRegen` | 电力回复速率 | 由核心模块决定 | `[PLACEHOLDER]` |
| `Heat` | 当前热量 | **只涨不自动降** | 0 |
| `HeatDissipation` | 散热速率 | 由底盘／辅助模块决定 | `[PLACEHOLDER]` |
| `OverheatThreshold` | 过热阈值 | 触发锁定 | `[PLACEHOLDER]` |

**热量是"反向资源"**，这是战斗节奏的核心杠杆：
- 攻击、冲刺、过载都会加 Heat。
- Heat 只能通过散热动作（暂停攻击、专用散热技能、环境冷却区）下降。
- Heat 达到阈值触发 `GameplayTag.State.Overheated`，锁定武器 2 秒 `[PLACEHOLDER]`。

**设计意图**：制造"爆发窗口—强制停顿"的节奏，让玩家主动规划输出节奏，而不是无脑连打。这是 P1 支柱在战斗层的落点。

**验证路径**：纸面模拟（Excel 算 3 种模块组合的"可持续输出时间"）→ 首个可玩原型记录 10 局实战 → 观察玩家是否主动管理热量。**如果玩家从不看热量条，说明杠杆失效，需重画。**

### 3.4 移动与攀爬

**基础**：CMC ＋ Enhanced Input。

**三种机体的移动差异（必须让玩家一上手就感觉到）**：

| 机体 | 移动特征 | 自定义 MovementMode |
|---|---|---|
| 轻型双足 | 二段跳、空中冲刺、墙面蹬跳 | `MOVE_Custom_1` 空中冲刺 |
| 中型通用 | 标准跑跳、钩索 | `MOVE_Custom_2` 钩索牵引 |
| 重型四足 | 慢速、高抗性、磁吸足攀爬 | `MOVE_Custom_3` 表面吸附 |

**攀爬实现要点**：
- 磁吸攀爬用自定义 MovementMode：检测法线 → 对齐角色朝向到表面 → 重力替换为吸附力。
- 不要用 "特殊移动体积"（NavLink ＋ 动画蒙太奇）糊弄攀爬——玩家会立刻感觉到"这不是真的在爬"。
- 攀爬是重型机的核心卖点，也是支柱 P1 的落点：换机体 → 换可达路线。

### 3.5 敌人 AI

**StateTree 结构示例（一个具名敌人）**：

```
Root
├─ State: Patrol        巡逻，感知玩家
├─ State: Engage        交火，按部位受损切换攻击模式
│   ├─ Task: 选择攻击部位（根据自身部位存活情况）
│   └─ Task: 移动到有效射程（EQS 查询掩体与射界）
├─ State: Staggered     核心暴露，进入可修复/可招募窗口
└─ State: Disabled      核心被毁，瘫痪可交互
```

**要点**：
- 敌人复用 `UPartDamageComponent`，与玩家同一套系统。**同一套代码，两种体验**——这是架构上的关键收益。
- 具名敌人的攻击模式随部位存活变化（打断手臂 → 改用近战），这是"拆解有策略"在敌方侧的体现。
- EQS 查询掩体与射界，避免敌人排队送死。
- 普通敌人用轻量 AI（简化 StateTree），具名敌人用完整状态机。**不要给 20 种敌人都写完整状态机。**

### 3.6 回收与经济系统

**Sources & Sinks 模型**（这是改装玩法能否立住的地基）：

| Sources（材料从哪来） | Sinks（材料到哪去） |
|---|---|
| 拆解敌人（主要来源） | 制造模块 |
| 区域残骸／宝箱 | 制造机体框架 |
| 任务奖励 | 修复机体与部位 |
| 基地回收站（被动产出） | 升级模块等级 |
| — | 基地建设（同伴设施） |

**通胀风险与对策**：

> **风险**：拆解是无限来源，玩家刷同一区域就能无限产出材料，模块价格迅速失去意义。

**对策（三条同时上）**：
1. **模块用"蓝图 ＋ 稀有核心"解锁，材料只做消耗。** 稀有核心只来自具名敌人和关键任务，数量有限，不可刷。
2. **区域材料衰减**：同一区域重复清剿，材料产出递减（`[PLACEHOLDER]` 递减曲线）。
3. **基地建设消耗大量材料**，作为长期 sink，吸收通胀。

**验证路径**：用 Monte Carlo 模拟 3 类玩家（速通型／收集型／刷子型）在 30 小时内的材料存量曲线。若刷子型的存量在 10 小时后趋于无限，说明 sink 不足。

### 3.7 移动基地与关卡流送

**两种流送策略，按关卡类型分开用**：

| 关卡类型 | 方案 | 理由 |
|---|---|---|
| 5 个大型区域 | **World Partition ＋ HLOD** | 需要大范围流送与 HLOD 简化 |
| 主基地（移动城市内部） | **传统子关卡流送（Level Streaming）** | 空间紧凑、逻辑复杂，World Partition 反而难控 |
| 巨像关卡 | **单关卡 ＋ 分段加载** | 巨像是受控运动的整体，不适合按空间切分 |

**移动基地的实现**：
- 基地是 Persistent Level 里的一个 `ALevelInstance` Actor。
- 基地移动是**受控的、脚本化的**，不做真实物理模拟整座城市。
- 基地内部空间用子关卡流送，进入室内时卸载外部区域。
- 玩家在基地内看到同伴设施随进度变化——这是"选择有后果"的可视化。

**5.8 新工具用起来**：World Partition Insights 可以按单元分析流送性能并回放会话，这是排查"为什么进这个区域会卡一下"的直接工具。

### 3.8 存档系统

**存档粒度决策（这是一个真实的设计张力）**：

> PC 单机玩家默认期待"随时存档"。但这个游戏里，随时存档意味着要序列化：机体装配状态、40 个模块的归属、掉落物在世界中的位置、敌人部位 HP、同伴关系、基地建设进度——状态空间巨大，且容易出 bug。

**决策**：**检查点式自动存档 ＋ 手动存档槽**，不做随时快速存档。
- 任务内设 2—3 个检查点，符合 20—40 分钟的单局节奏。
- 玩家可在主基地手动存档到多个槽位。
- 存档点位置与任务节拍对齐（准备后、张力中、回收前）。

**版本迁移**：
- `USaveGame` 子类带 `SaveVersion` 字段。
- 每次改动存档结构，写一个迁移函数。
- **从 P2 起，每次迭代都必须用旧版本存档测试读取**。这一条不做，上线后玩家存档损坏会是最致命的差评来源。

### 3.9 UI

**技术**：Common UI ＋ MVVM。

**优先级最高的三个界面**（按实现顺序）：

1. **改装界面** —— 承载支柱 P1，必须最早做。要求：实时预览机体形态；三条约束的实时数值反馈；对比当前配置的差异高亮。
2. **任务简报／地图** —— 承载支柱 P3 的"准备"节拍。
3. **战斗 HUD** —— 热量条、电力条、部位损伤提示。

**关键 UX 决策**：改装界面必须让玩家**在不离开界面的情况下看到重量/供电/散热的变化**。如果玩家要来回切换界面才能判断配置是否可行，改装就会从"乐趣"变成"算账"。

### 3.10 音频

| 需求 | 方案 |
|---|---|
| 机器人语音（非人声但有情绪） | MetaSounds 合成，音高／滤波随情绪参数变化 |
| 引擎声随负载变化 | MetaSounds 参数绑定移动速度与热量 |
| 战斗节奏同步 | Quartz 节拍同步 |
| 调试 | Audio Insights（5.8 生产就绪） |

**设计要点**：机器人角色不使用人类配音演员的人声，而用**合成音 ＋ 字幕**。理由是角色设定一致性（它们不是人），同时显著降低成本，并规避多语言配音的规模问题。

### 3.11 演出与过场

**严格控制过场数量**。重点投入 4 场：

| 场次 | 内容 | 目的 |
|---|---|---|
| 开场 | 拾壹获得跨机体迁移能力 | 建立世界观与核心机制 |
| 启程 | 灯塔移动城市首次启动 | 展示"大制作感"的规模 |
| 巨像 | "行走的暴风雪"关卡收束 | 核心卖点的高光时刻 |
| 终局 | 全球强制回收程序终止 | 情感落点 |

其余区域用**环境叙事 ＋ 同伴对话**承担，不做全过场。每多一场高成本过场，就少一批可玩内容——这是必须守住的取舍。

## 4. 系统交互矩阵

提前暴露系统打架的风险。标注每对系统的关系：**Intended**（预期）／**Acceptable**（可接受）／**Bug**（必须修）。

| 系统 A | 系统 B | 关系 | 说明 |
|---|---|---|---|
| 部位拆解 | 移动系统 | Intended | 腿部部位被毁 → 移动受限，这是核心体验 |
| 部位拆解 | 动画系统 | Intended | 部位隐藏后动画必须适配（缺手臂的射击动作） |

| 改装 | 存档 | **Bug 风险** | 改装后存档再读档，模块归属必须一致。需专项测试 |
| 改装 | 经济 | Intended | 稀有核心限制改装节奏 |
| 热量系统 | 敌人 AI | Intended | 敌人应利用玩家过热窗口进攻 |
| 热量系统 | UI | Intended | 热量条必须是 HUD 最显眼元素之一 |
| 攀爬 | 流送 | **Bug 风险** | 攀爬时跨流送单元 → 可能加载卡顿导致坠落。需攀爬路径预加载 |
| 移动基地 | 存档 | Acceptable | 基地位置不需精确存档，只需存进度标记 |
| 同伴系统 | 任务流程 | **Bug 风险** | 同伴招募顺序不同 → 任务对话分支组合爆炸。需限制同伴入队时机 |
| MegaLights | 性能 | Acceptable | 需按场景设光源上限，工业场景易超标 |
| Control Rig Physics | 稳定性 | **Bug 风险** | 测试版功能，需回退方案（退回手 K 动画） |

**这张表在每个里程碑评审时重新过一遍**，新系统加入必须补一行。

## 5. 美术与动画管线

### 5.1 机器人建模规范（外包交付必须遵守）

| 项目 | 规范 |
|---|---|
| 单位与比例 | 厘米制，1 单位 = 1 cm |
| 朝向 | 统一 +X 朝前，+Z 朝上 |
| Pivot | 模块 Pivot 统一在挂点中心，不允许在包围盒中心 |
| 挂点命名 | `socket_head`、`socket_arm_L`、`socket_arm_R`、`socket_back`、`socket_aux_01…` |
| 骨架 | 3 类机体各有独立骨架，但共享 IK Rig 定义以复用动画 |
| 三角面预算 | 主角机体 15—25 万；具名敌人 6—10 万；普通敌人 3—6 万；模块 2—8 千 |
| 贴图 | 部件 1024，机体主体 2048，统一 sRGB 与法线格式 |
| 材质槽 | 每个模块最多 2 个材质槽（限制 draw call） |
| LOD | 4 级自动生成 ＋ 手动修正，LOD1 起减面 ≥ 50% |
| UV | 模块共享 UV 布局规范，便于材质复用 |

### 5.2 环境美术

- **Nanite 用于静态环境几何**（巨构、建筑、地形）。
- **骨骼网格体走标准 LOD 管线**，不依赖 Nanite。
- 区域模块化：每个区域用统一的模块化构件集，降低建模成本并加快关卡搭建。
- **PCG 用于散布**：废墟残骸、管道、植被。PCG 节点优先用稳定版，实验性节点不进生产管线。
- **程序化植被编辑器（实验性）**：仅用于概念探索，不用于最终资产。

### 5.3 动画管线

| 环节 | 方案 |
|---|---|
| 3 类机体共享动画 | IK Retargeter ＋ 共享 IK Rig 定义 |
| 状态机 | 每类机体一个 AnimBP，共享基础层 |
| 攻击对齐 | Motion Warping（攻击时自动对齐目标） |
| 次级运动 | Control Rig Physics（天线、线缆、液压管）—— **测试版，必须有回退方案** |
| 程序化脚步 | 足部 IK ＋ 地形适配（重型四足在不平地面必须踩实） |

**外包交付包必须包含**：UE 工程模板、命名规范文档、Pivot/朝向验收清单、LOD 与材质槽检查工具。**没有验收工具的资产不要收**——否则返工成本会吃掉外包省下的钱。

## 6. 性能预算与门禁

### 6.1 目标配置

| 档位 | 硬件参考 | 分辨率／帧率 | 画质预设 |
|---|---|---|---|
| 最低 | GTX 1660 / Ryzen 5 3600 | 1080p / 30fps | 低（Lumen Lite 关闭，烘焙光照） |
| 基准 | RTX 3060 / Ryzen 5 5600 | 1080p / 60fps | 中（Lumen Lite ＋ MegaLights 限流） |
| 推荐 | RTX 4070 / Ryzen 7 5800X | 1440p / 60fps | 高（完整 Lumen） |
| 高端 | RTX 4080+ | 4K / 60fps | 极高 |

### 6.2 帧预算（基准档 1080p/60fps，总预算 16.6 ms）

| 项 | 预算 | 说明 |
|---|---|---|
| 游戏线程 | 6.0 ms | 含 AI、动画、物理 |
| 渲染线程 | 8.0 ms | 含 Lumen、MegaLights |
| GPU | 14.0 ms | — |
| 预留 | 2.6 ms | 波动余量 |

**硬性上限**：
- Draw call：< 5000（1080p 基准档）
- 同屏敌人：≤ 12 个普通敌人 或 4 个具名敌人 `[PLACEHOLDER]`
- 同屏掉落物：≤ 20 个，超出后最早的自动转静态 `[PLACEHOLDER]`
- 同屏 MegaLights 光源：≤ 32 `[PLACEHOLDER]`
- VRAM：< 8 GB @ 1080p 中画质

### 6.3 性能门禁

**每个里程碑设性能门禁，不达标不进入下一阶段。** 这是唯一能防止"上线前发现跑不动"的机制。P2 结束时必须达到基准档 60fps，否则先优化再扩内容。

## 10. 前 14 天执行清单

这是一份可以直接照做的启动清单。目标不是做出游戏，而是**在两周内拿到"这个核心循环是否成立"的第一个信号**。

| 天 | 任务 | 产出 |
|---|---|---|
| D1—D2 | 安装 UE 5.8；搭建 Perforce 或 Unreal Revision Control 仓库；建立工程目录与命名规范文档 | 可提交的空工程 |
| D3—D4 | 建立 C++ 模块骨架（RobotCore / RobotCombat / RobotAssembly）；接入 Enhanced Input；做出能跑能跳的胶囊体 | 可操控的灰盒角色 |
| D5—D6 | 接入 GAS；实现 Power / Heat 两条属性；做一个消耗电力、产生热量的冲刺技能；过热锁定 | 能感受到"爆发—停顿"节奏的移动 |
| D7—D8 | 实现 `UPartDamageComponent`；做骨骼名 → 部位 Tag 的映射 DataAsset；做一个木桩敌人，打腿会瘸 | 部位伤害可验证 |
| D9—D10 | 部位破坏 → 隐藏骨骼 ＋ Spawn 备件掉落物 → 拾取 → 材料计数 | 回收闭环跑通 |
| D11—D12 | 做最丑但能用的改装界面：3 个插槽，换装真实改变移动速度与攻击方式 | 换装影响玩法 |
| D13—D14 | 自测 10 局，记录三个数据：玩家是否主动换装？换装后是否感知差异？玩家看热量条吗？ | 一份自测报告 ＋ 下一步决策 |

**D14 的决策规则**：
- 三个数据都正向 → 进入 P1，扩充模块数量与关卡。
- 换装无感知 → 停下来重画改装系统，不要继续加内容。
- 玩家不看热量条 → 热量杠杆失效，简化或替换机制。

**这份清单最重要的作用不是产出，而是把"这个游戏好不好玩"这个模糊问题，变成两周内可以拿到答案的具体实验。**
